# Destructor in C++ — Basic to Advanced (Revision Notes

> Ye notes tumhare `Customer` class (dynamic pointer `balance` wale) code pe based hain. Destructor **bilkul shuru se advanced tak** cover kiya hai — pointer memory allocation ka deep concept, aur constructor/destructor call order ki dependency bhi.

---

## PART 1: BASICS

### 1.1 Destructor kya hota hai?

**Definition:** Destructor ek **special member function** hota hai jo object ke **"marne" (destroy hone)** ke time automatically call hota hai. Iska kaam hai object ne jo bhi **resources (jaise dynamic memory) allocate ki thi**, unhe **clean-up/free** karna.

**Syntax Rules:**

1. Naam class ke jaisa hi hota hai, lekin aage **`~` (tilde)** lagta hai: `~Customer()`
2. **Koi return type nahi** hota (constructor jaisa hi).
3. **Koi parameter nahi le sakta** — sirf **ek hi destructor** ho sakta hai class mein (destructor **overload nahi** ho sakta, constructor ki tarah).
4. **Kabhi khud call nahi karte** — ye **automatically** call hota hai.

```cpp
class Customer {
public:
    Customer() { cout << "Constructor called\n"; }
    ~Customer() { cout << "Destructor called\n"; }   // <- destructor
};
```

**Analogy:** Agar Constructor ek **naya ghar banwana (setup karna)** hai, to Destructor uska ulta — **ghar khaali karke, saara saaman wapas karke, bijli-paani connection cut karke, keys jama karna (cleanup)** hai. Jaise checkout time pe hotel room khaali karte waqt saara saaman samet ke jaana padta hai — waise hi destructor object ke "checkout" (destroy) hone se pehle sab kuch clean karta hai.

---

### 1.2 Destructor Kab Automatically Call Hota Hai?


| Situation                  | Kab Call Hoga                                                     |
| -------------------------- | ----------------------------------------------------------------- |
| **Static/Stack object**    | Jaise hi uska scope (function/block) khatam hota hai              |
| **Dynamic object (`new`)** | Jab tum manually`delete`karte ho                                  |
| **Program khatam ho**      | Saare bache hue static/global objects ka destructor call hota hai |

```cpp
void func() {
    Customer c1("Yash", 1000);   // constructor call
}   // <- yahan c1 ka scope khatam, destructor AUTOMATICALLY call hoga

int main() {
    Customer *A1 = new Customer("Yash", 1000);  // constructor call
    delete A1;    // <- destructor SIRF ISI LINE PE call hoga, warna kabhi nahi hoga!
}
```

> **Tumhara comment bilkul sahi tha:***"iski wajah se hamara destructor call hota, warna nahi hota kyunki hamne dynamic object banaya tha"* — Ye **100% correct hai**. Dynamic (`new` wale) objects ka destructor **kabhi apne aap call nahi hota** — sirf `delete` karne se hi hota hai. Agar `delete` bhool gaye, to destructor kabhi nahi chalega → **memory leak**.

## PART 2: DEEP DIVE — POINTER MEMORY ALLOCATION (Jo Tumne Specifically Pucha)

Tumhare code mein ek bahut important concept hai jo dhyan se samajhna chahiye:

```cpp
class Customer {
    string name;
    int *balance;      // ye ek POINTER hai, int nahi!

public:
    Customer(string name, int bal) {
        this->name = name;
        balance = new int;   // STEP 1
        *balance = bal;      // STEP 2
    }
};
```

### Step-by-Step Kya Ho Raha Hai:

**Step 1: `balance = new int;`**

* `int *balance;` sirf ek **pointer variable declare** karta hai — abhi tak ye kisi valid memory ko point **nahi** kar raha (garbage/undefined address hai).
* `new int`**heap pe ek naye `int` ke size ki (4 bytes) memory allocate** karta hai, aur us memory ka **address return** karta hai.
* Wo address `balance` mein **store** ho jaata hai — ab `balance`**valid heap memory ko point** kar raha hai.

```
STACK (ya jahan Customer object hai)      HEAP
┌───────────────┐
│ balance (ptr)   │  ---address---> ┌─────────────┐
│ (address stored)│                 │  [empty int]  │  <- abhi koi value set nahi hui, garbage hai
└───────────────┘                 └─────────────┘
```

**Step 2: `*balance = bal;`**

* `*balance` matlab — jo address `balance` ke andar store hai, **wahan jaake (dereference karke) value likho**.
* Yahan `bal` (jo constructor ko diya gaya parameter hai, jaise `1000`) us heap memory location pe **store** ho jaata hai.

```
STACK                                      HEAP
┌───────────────┐
│ balance (ptr)   │  ---address---> ┌─────────────┐
│ (address stored)│                 │  1000         │  <- ab value set ho gayi
└───────────────┘                 └─────────────┘
```

**Analogy:** Ye bilkul aisa hai jaise:

1. **Step 1 (`new int`)** = Tumne bank mein jaake **ek naya khaali locker book** kiya. Bank tumhe locker ka **number/address (chaabi)** deta hai — abhi locker **khaali** hai.
2. **Step 2 (`*balance = bal`)** = Ab tum us locker ko **chaabi se khol ke usme paisa (value) rakh rahe ho**.

### Ye Do Steps Ek Line Mein Bhi Ho Sakte The:

```cpp
balance = new int(bal);   // allocate + initialize ek saath (better practice)
```

Lekin tumhare code mein jo do-step wala tareeka hai, wo bhi bilkul sahi hai — sirf explicit tareeke se dikhaya gaya hai ki **allocation** aur **value assignment****do alag kaam** hain.

### Important: Ye Pointer Sirf 1 `int` Ke Liye Hai, Array Nahi!

```cpp
balance = new int;        // sirf EK int ke liye memory (4 bytes)
balance = new int[100];   // 100 ints ke liye memory (array) — is case mein `delete[]` chahiye, `delete` nahi!
```

Tumhare code mein sirf **ek** int allocate ho raha hai (`new int`), isiliye destructor mein `delete balance;` (bina `[]` ke) sahi hai.

## PART 3: DESTRUCTOR MEMORY CLEANUP

```cpp
~Customer() {
    cout << "Destructor free all the memory, dynamic memory release karayega";
    delete balance;    // heap wali memory wapas OS ko de di
}
```

**`delete balance;` kya karta hai:**

* Jo memory `new int` se allocate hui thi, wo **heap ko wapas return** kar deta hai — ab OS us memory ko kisi aur ke liye use kar sakta hai.
* `balance` pointer khud (variable) to memory se hata nahi (wo to object ke saath khatam hoga), bas usne jis heap memory ko point kiya tha, wo free ho gayi.

> **Golden Rule:** Jitni baar `new` kiya hai, utni baar `delete` karna zaroori hai — ye **1:1 pairing** honi chahiye. Agar `new int[]` kiya hai (array), to `delete[]` use karo, sirf `delete` nahi (warna undefined behavior ho sakta hai).

## PART 4: CONSTRUCTOR vs DESTRUCTOR — CALL ORDER DEPENDENCY (Jo Tumne Specifically Pucha)

Ye sabse **advanced aur important concept** hai — chalo isse bilkul depth mein samajhte hain.

### 4.1 Basic Rule: Destructor Order Constructor Ka **Ulta (Reverse)** Hota Hai

**Jab multiple objects bante hain (jaise ek function ke andar), unka construction order top-to-bottom hota hai, lekin destruction order bottom-to-top (reverse) hota hai.**

```cpp
void func() {
    Customer c1("A", 100);   // 1st constructor call
    Customer c2("B", 200);   // 2nd constructor call
    Customer c3("C", 300);   // 3rd constructor call
}   // yahan function khatam ho raha hai...
    // Destructor order: c3 destroy hoga PEHLE, fir c2, fir c1 (REVERSE ORDER!)
```

**Output:**

```
Constructor called (A)
Constructor called (B)
Constructor called (C)
Destructor called (C)   <- last bana, sabse pehle destroy hua
Destructor called (B)
Destructor called (A)   <- pehla bana, sabse aakhir mein destroy hua
```

**Analogy — STACK OF PLATES:** Yaad hai humne pehle Stack Memory ko **plates ka dhera** bataya tha (LIFO — Last In, First Out)? Yehi cheez yahan bhi ho rahi hai:

* Jaise plates upar rakhte jaate ho (c1, fir c2, fir c3 upar) — ye **construction order** hai.
* Jab hatana ho, to **sabse upar wali plate (c3) sabse pehle uthegi**, fir c2, fir sabse neeche wali c1 sabse last mein — ye **destruction order** hai.

**Kyu aisa hota hai?** Kyunki ye objects **Stack memory** pe bante hain, aur Stack **LIFO** follow karta hai. Jo sabse last mein stack pe "push" hua, wo destroy hote waqt sabse pehle "pop" hoga.

---

### 4.2 Composition Mein Dependency (Object Ke Andar Object)

Agar ek class ke andar **doosri class ka object bhi member ho** (composition), to construction/destruction order aur bhi important ho jaata hai.

```cpp
class Engine {
public:
    Engine() { cout << "Engine ON (Constructor)\n"; }
    ~Engine() { cout << "Engine OFF (Destructor)\n"; }
};

class Car {
    Engine e;     // Car ke andar Engine ka object hai (composition)
public:
    Car() { cout << "Car Built (Constructor)\n"; }
    ~Car() { cout << "Car Destroyed (Destructor)\n"; }
};

int main() {
    Car myCar;
}
```

**Output:**

```
Engine ON (Constructor)     <- pehle andar wala (Engine) bana
Car Built (Constructor)     <- fir bahar wala (Car) bana
Car Destroyed (Destructor)  <- pehle bahar wala (Car) destroy hua
Engine OFF (Destructor)     <- fir andar wala (Engine) destroy hua
```

**Rule:** Construction mein **members (andar ke objects) pehle bante hain**, fir outer class ka apna constructor chalta hai. Destruction mein **bilkul ulta** — pehle outer class ka destructor chalta hai, fir members (andar ke objects) destroy hote hain.

**Analogy:** Ye bilkul **gift-wrapping** jaisa hai:

* **Banate waqt:** Pehle andar wali cheez (gift/Engine) rakhte ho box mein, fir bahar se wrapping paper (Car) lagate ho. (Andar wala pehle "ready" hota hai)
* **Kholte waqt:** Pehle bahar ka wrapping paper (Car) hataoge, tab jaake andar ka gift (Engine) dikhega aur nikaalenge. (Bahar wala pehle "hataya" jaata hai)

**Isiliye ye ek "dependency" hai:** Engine, Car ke bina exist ho sakta hai, lekin Car ko banne ke liye Engine chahiye hi hoga — isliye Engine **pehle** ban ke "ready" hona chahiye. Destroy karte waqt, pehle **Car ko khatam karo** (jo Engine use kar raha tha), tabhi safely Engine ko destroy karna sahi hoga — warna Car abhi bhi ek destroyed Engine ko use karne ki koshish kar sakta tha (crash ho sakta tha).

---

### 4.3 Inheritance Mein Bhi Yahi Reverse Rule Chalta Hai

```cpp
class Base {
public:
    Base() { cout << "Base Constructor\n"; }
    ~Base() { cout << "Base Destructor\n"; }
};

class Derived : public Base {
public:
    Derived() { cout << "Derived Constructor\n"; }
    ~Derived() { cout << "Derived Destructor\n"; }
};

int main() {
    Derived d;
}
```

**Output:**

```
Base Constructor        <- Base (parent) pehle banta hai
Derived Constructor     <- fir Derived (child) banta hai
Derived Destructor      <- Derived pehle destroy hota hai
Base Destructor         <- fir Base destroy hota hai
```

**Same logic:** Child (Derived) ko banne ke liye Parent (Base) ka structure pehle ready chahiye — isliye Base constructor pehle chalta hai. Destroy karte waqt pehle child ko hatao, fir uske parent ko — kyunki child, parent ke upar depend karta hai.

---

### 4.4 Kyu Ye "Dependency" Wala Concept Itna Important Hai?

Agar ye reverse order na follow hota, to problems aa sakti thi:

* Agar Engine pehle destroy ho jaata aur Car ka destructor baad mein chalta jo Engine ko use karne ki koshish karta — to **crash (use-after-free)** ho jaata.
* Agar Base class pehle destroy ho jaati aur Derived class abhi bhi Base ke members use karne ki koshish karta — wahi problem.

**Isliye C++ language design mein hi ye guarantee hai:***"Jo cheez baad mein bani, wo dependent hai un cheezo pe jo usse pehle bani thi — isliye use pehle khatam karna hoga, taaki uski dependencies (jinpe wo depend karta tha) safely baad mein khatam ho sakein."*

## PART 5: PURA FLOW — TUMHARE CODE KE SAATH

```cpp
int main() {
    Customer *A1 = new Customer("Yash", 1000);
    // Output: "Constructor is called"
    // balance ke liye heap memory allocate hui, 1000 store hua

    delete A1;
    // Output: "Destructor free all the memory, dynamic memory release karayega"
    // balance wali heap memory free ho gayi
}
```

Agar `delete A1;` line **nahi hoti**, to:

* `main()` khatam ho jaata, program close ho jaata.
* `A1` (pointer) khud to stack se hat jaata (kyunki wo local variable tha), **lekin jis heap memory ko wo point kar raha tha, wo kabhi free hi nahi hoti** — destructor kabhi call hi nahi hota → **memory leak** (chhota sa leak hota, kyunki program hi close ho raha hai OS wapas le lega, lekin agar ye kisi bade running program mein hota jahan baar baar aisa hota rahta, to serious memory leak ban jaata).

## PART 6: QUICK RECAP TABLE (Interview-Ready)


| Concept                     | Detail                                                                                                                          |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Destructor naam             | `~ClassName()`                                                                                                                  |
| Return type                 | Nahi hota                                                                                                                       |
| Parameters                  | Nahi le sakta, overload nahi ho sakta                                                                                           |
| Kab call hota (static obj)  | Scope khatam hote hi, automatic                                                                                                 |
| Kab call hota (dynamic obj) | Sirf`delete`karne pe, kabhi apne aap nahi                                                                                       |
| Kaam                        | Dynamic memory / resources free karna                                                                                           |
| `new int`vs`new int[]`      | Pehle wale ke liye`delete`, doosre ke liye`delete[]`                                                                            |
| Multiple objects order      | Construction: top-to-bottom, Destruction: bottom-to-top (**reverse**)                                                           |
| Composition order           | Andar wala member pehle banta hai, baad mein destroy hota hai                                                                   |
| Inheritance order           | Base pehle banta hai (Constructor), Derived pehle destroy hota hai (Destructor)                                                 |
| Reverse order kyu           | Taaki dependent cheez (jo kisi doosri cheez pe depend karti hai) pehle safely hat jaaye, uske baad hi uski dependency khatam ho |
